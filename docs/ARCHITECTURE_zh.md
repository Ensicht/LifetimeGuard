# LifetimeGuard 项目架构

## 1. 范围与设计约束

LifetimeGuard 是 Windows x64 的 REFramework 原生插件，围绕异步文件读取和纹理任务寿命提供四项有边界的保护。它不负责替换模型、选择外观、加载资源列表或修复任意游戏等待状态。

运行代码遵循事件驱动、身份与代次配对、固定容量、有界诊断及兼容性拒绝原则。文件租约与带任务纹理收尾限定在加载期；失败纹理重读及特定松散纹理清理配对可在正常游玩期由已有原生事件触发。正常游玩不通过持续扫描发现资源。

发布版源码移除自有运行代码注释，含注释版保留中文函数说明。两者使用同一编译参数和导出接口，差异不形成调试开关、运行策略或性能档位。安装使用说明以根目录 README 为准，构建接口见 `BUILD_zh.md`。

## 3. 四项保护

### 3.1 加载期文件寿命

读取请求登记时为文件建立租约，保留异步读取仍需要的引用。Close 入口发现存在未完成租约时暂缓关闭；最后一个租约完成后重放延迟 Close 并释放对应引用。不能将引用数的某个取值单独解释为所有权。

请求按地址、文件身份及代次配对。文件表与请求表使用固定容量和有限探测，容量耗尽必须保留明确的拒绝路径，不扩展为无界分配。文件相关锁、请求登记顺序及原子内存序共同承担并发正确性。

加载门关闭后不接受新的普通文件租约，但已经登记的请求继续排空。排空过程与是否允许新保护是两个不同状态。

### 3.2 加载期纹理收尾

只有受保护代次中的纹理任务、有效布局和满足策略的异常终态才能进入修正。非纹理、未知宿主、无效结构及不满足条件的完成量继续原有流程或拒绝接入，不把任意资源强制置为 Ready。

策略层决定是否具备处理资格，原生适配层负责读取结构和调用入口，两者的检查不能互相替代。

### 3.3 失败纹理有界重读

恢复入口来自原生失败终态、ready 查询和删除回调。身份检查覆盖资源、代次、引用、任务、运行时纹理和销毁状态；指针地址复用不代表同一资源仍然存活。删除或代次变化必须使旧身份失效。

正常游玩最多四个恢复任务同时在途。再次失败采用 250 毫秒、1 秒、5 秒、30 秒的退避，后续保持 30 秒；再次出现合格事件时才判断是否到期，不由周期扫描触发。累计失败次数不会单独永久禁用恢复。

提交原生重读与纹理最终可见是不同阶段。计数和界面不能将提交成功解释为已经恢复显示，也不能把被处理事件数量解释为避免卡死的数量。

### 3.4 松散纹理清理引用配对

仅对符合调用地址、宿主及 `.tex.数字` 路径条件的清理 Close 入口增加一次临时引用，与其后两次原生释放配对。它不是面向所有 Close 的额外 AddRef，也不建立跨帧资源持有缓存。

该路径可在正常游玩期触发。宿主不符合条件时拒绝此项，其他保护仍按各自能力判断，不绕过检查扩大适用范围。

## 4. 加载门状态契约

普通加载由 `EnvironmentManager.evSceneLoadBefore` 开门。Player/Environment 的 load-end 是接近结束的证据，不能单独关门。既有 `UpdateMotion` 回调只在门开启时读取 Loading，关闭要求同时满足：当前 `Loading=false`、本代次已收到 load-end 或曾观察到 `Loading=true`、当前 Scene 或 MainView 非空。

同场景黑屏由 `mcFastTravel.setupLoadingEvent` 建立需要 fade-in 的代次，等待 `CameraManager.onSceneLoadFadeIn`。较早的 Player load-end 不应解除这个等待。

生命周期接入完整后，bootstrap 门覆盖第一个真实起点前的启动读取，首个真实起点接管该代次。缺少完整起止能力时旁路，不退化为永久开启。门不活跃时 UpdateMotion 路径直接返回。

## 5. 原生接入与并发所有权

原生接入分别检查模块指纹、x64 指令、虚表、返回地址及内存可读性。DirectStorage 兼容条件、游戏入口条件和松散清理宿主条件是独立的能力边界，单项就绪不能证明其他项就绪。

MinHook 主入口分配失败时才考虑固定 16 字节后备，并继续要求对应指令和入口条件。固定入口后备不是通用 Hook 方案。未知指令、槽位冲突、内存分配失败或页面保护失败都应拒绝并回滚已完成的部分。

指针回滚只能恢复仍由本插件持有的槽位，不能覆盖其他参与者后来写入的值。锁内状态变更、释放发生点以及线程指令指针和栈展开处理属于行为契约，不作为样式清理调整。

文件表容量为 32768，请求表为 65536，两者探测上限均为 256；文件锁为 256 个。固定容量使最坏情况工作量有界。高频路径只保存必要标量，不把原生对象的延迟解引用任务交给报告线程。

## 6. 诊断、界面与配置

统计结构 ABI 的 `version=9` 是接口结构版本，不是发行版本 `0.6.0`。既有导出函数是接口的一部分；离线调用入口不会自行运行，也不需要随源码附带调用程序。

运行数据归属 `reframework/data/DStorageFileLifetimeGuard/`：

| 文件 | 语义 |
| --- | --- |
| `ui.ini` | 启动读取，用户切换语言时保存 |
| `events.log` | 当前会话事件 |
| `failures.log` | 有故障时产生的有限摘要 |

日志保留当前及此前八次历史。事件和故障通过编号、进程标识及启动时间对应；无故障会话允许缺号，不为连续编号移动旧故障。四类故障摘要各最多 16 条，安装细节最多 192 KiB。达到记录限额不应关闭保护。

后台报告线程只消费回调产生的有界快照并格式化写盘，不重新读取已经可能销毁的游戏对象。中英文面板展示同一统计状态，语言设置不改变保护行为；用户运行配置和日志不属于安装包资源。

## 7. 构建与扩展边界

自有代码采用 MIT，署名 Laz。修改后的 MinHook、REFramework API 头以及编译器运行库保留各自许可；第三方版权注释不能随自有代码注释一并移除。

构建只需要源码包中的依赖与显式指定的 LLVM-MinGW，不依赖游戏路径。`build.py` 输出生产 DLL，`package.py` 生成完整发布文件夹，其中包括安装 ZIP 和同级的许可证，不生成外层压缩包。内容标识与编译状态用于确认原版输入和产物匹配，不代表任何运行场景的结果。

修改加载结束条件、锁、引用计数、恢复条件、容量或原生签名均属于行为修改。增加新的宿主支持应保持能力分离和拒绝路径；避免引入持续场景扫描、额外重试定时器或未经所有权确认的引用操作。
